## Q1：素材库的页面形态

### 背景
旧架构中素材库（material-library）是独立工具页，承担：
- 选择达人、管理档案（人格档案/内容规划）
- 管理参考素材（6种类型）
- 展示红人采集信息（kol-intake数据）

新平台 M2 已有「KOL管理」页面（admin端），可以管理KOL基础信息和档案。

### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| **A. 整合进KOL管理页** | 在 `/admin/kols/[id]` 详情页增加「档案」「素材」两个 Tab | 数据集中、不重复、减少迁移工作量 | 素材操作入口变深（需先进详情页） |
| **B. 保留独立工具页** | 在 operator 端单独保留素材库页面，完整复刻旧版体验 | 操作习惯延续、入口平级 | 与KOL管理存在功能重叠 |
| **C. 拆分功能** | 档案管理 → 整合进KOL详情页；素材管理 → 独立素材库页面 | 职责分离清晰 | 工作量最大 |

**推荐方案**：A（整合进KOL详情页），参考素材的添加/删除频率不高，运营人员通过KOL详情页操作即可满足需求。

**决策结果**：`[ 待填写：A / B / C ]`

## Q2：复盘工具的权限位置

### 背景
人设脚本复盘、千川脚本复盘、直播复盘三个工具，旧架构无权限限制，任何人可用。
新平台需要明确放在管理员端（admin）还是运营端（operator）。

### 方案对比

| 方案 | 描述 | 适用场景 |
|---|---|---|
| **A. 放 operator 端** | 运营人员自己做复盘，各自管理各自的报告 | 运营人员有复盘需求，且各自负责不同账号 |
| **B. 放 admin 端** | 只有管理员可以做复盘，统一管理所有报告 | 复盘是管理层工作，运营只负责执行 |
| **C. 两端都有** | operator 端可生成复盘，admin 端可查看全部报告 | 运营做、管理看，职责分离 |

**推荐方案**：A（放 operator 端），复盘是运营日常工作，应由运营人员自主操作。

**决策结果**：`[ 待填写：A / B / C ]`

## Q3：个人工作产物的默认可见范围

### 涉及数据
以下三类数据是运营人员各自产生的工作内容：
- **红人采集问卷**（kol_submissions）：运营采集红人信息后提交的23项问卷
- **人设定位历史**（positioning_histories）：AI生成的人格档案+内容规划记录
- **复盘报告**（review_reports）：人设/千川/直播复盘的AI分析报告

### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| **A. 私有制** | 只有创建者本人可见，管理员可查看全部 | 数据隔离清晰，保护个人工作内容 | 协作不便，团队间无法互相参考 |
| **B. 团队共享制** | 所有运营人员都能看到全部记录，等同于旧架构 | 操作简单，协作方便 | 无数据归属感，不利于绩效追踪 |
| **C. 私有+可分享** | 默认只有自己可见，可主动分享给指定人或全员 | 兼顾隐私和协作 | 需要额外开发分享功能 |

**推荐方案**：A（私有制，管理员可查全部），MCN团队中不同运营人员负责不同账号，数据隔离更合理；如后续有协作需求再扩展分享功能。

**决策结果**：`[ 待填写：A / B / C ]`

## Q5：红人采集问卷的可见范围

### 背景
红人采集（kol-intake）提交的数据有两面性：
- 它是**运营工作产物**（运营人员去做的采集）
- 它也是**公共红人数据**（采集完后所有人都需要用这批数据，例如人设定位时"从kol-intake导入"）

### 方案对比

| 方案 | 描述 | 说明 |
|---|---|---|
| **A. 提交人+管理员可见** | 与 Q3 保持一致，采集问卷归属提交人 | 如果运营各自负责不同红人，数据不会混淆 |
| **B. 所有人可见** | 问卷提交后全员可查看，因为红人是公共资产 | 适合统一管理多个红人账号的团队 |
| **C. 提交时可选** | 提交问卷时选择「仅我可见」或「全员可见」 | 灵活但增加用户决策成本 |

**推荐方案**：B（所有人可见），红人信息本质上是团队共用的基础数据，不同于个人创作的复盘报告。

**决策结果**：`[ 待填写：A / B / C ]`

## Q6：共享工具 API 路径规划

### 背景
人设仿写、千川仿写、产品卖点提取、复盘工具都需要调用：
- `/api/chat`（AI流式对话）
- `/api/transcribe/upload`（视频转录）
- `/api/transcribe/poll`（轮询转录）
- `/api/fetch-video`（TikHub视频解析）
- `/api/export-word`（导出Word）

### 方案对比

| 方案 | 路径风格 | 说明 |
|---|---|---|
| **A. 统一工具路径** | `/api/tools/chat`、`/api/tools/transcribe/upload` 等 | 与业务API（/api/kols）明确分区，职责清晰 |
| **B. 保持扁平路径** | `/api/chat`、`/api/transcribe/upload` 等 | 与旧架构路径相同，前端改动最小 |

**推荐方案**：A（统一工具路径），避免与业务API混淆，利于后期维护。

**决策结果**：`[ 待填写：A / B ]`

## Q7：M2 已有表的数据归属补充

### 背景
M2 阶段创建的以下表目前没有 `createdBy` 字段：
- `kols`（红人）
- `products`（产品）
- `materials`（参考素材）

这些数据由管理员录入后全员共用，目前设计是合理的。
但需要确认：**运营人员是否也可以新增 KOL / 产品 / 素材？**

### 方案对比

| 方案 | 描述 |
|---|---|
| **A. 仅管理员增删改，运营只读** | kols/products/materials 的写操作受角色限制，运营端只展示不可编辑 |
| **B. 运营也可以新增（不可删改他人记录）** | 运营可以新增KOL和素材，但不能修改或删除其他人创建的记录 |
| **C. 完全开放** | 所有角色均可增删改，等同于旧架构 |

**推荐方案**：A（仅管理员写，运营只读），kols/products 是平台基础数据，应由专人维护，避免运营误操作导致数据混乱。

**决策结果**：`[ 待填写：A / B / C ]`
